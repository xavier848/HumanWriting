Hypothesenbildung und technisches Konzept der Datenerhebung

Nachdem in den vorangegangenen Kapiteln die theoretischen und technischen Grundlagen dargelegt wurden, werden im Folgenden die Hypothesen der Arbeit aufgestellt und hergeleitet. Die Hypothesen beruhen überwiegend auf eigenen Überlegungen und beziehen sich sowohl auf die Metadaten der Videos, also insbesondere Aufrufe, Likes und Kommentaranzahl, als auch auf deren Platzierung innerhalb der Trends. Insgesamt werden fünf Thesen formuliert, die drei Bereiche abdecken: die Zusammensetzung der Trends und deren Einfluss auf die enthaltenen Videos, die Struktur der Kommentare anhand zuvor definierter Kategorien sowie eine indirekte Bewertung der Videos über eine Sentimentanalyse der Kommentare.

Die erste Hypothese betrifft die Popularität der Trendvideos. Diese soll zum einen über das Verhältnis von Likes zu Dislikes und zum anderen über das Sentiment der Kommentare gemessen werden. Es wird erwartet, dass Trendvideos deutlich mehr Likes als Dislikes erhalten, das Sentiment der Kommentare jedoch neutral ausfällt oder zumindest schlechter ist, als es die Like-Rate vermuten ließe. Dahinter steht die Überlegung, dass Zustimmung häufig nur über einen Klick auf den Like-Button ausgedrückt wird, während Kritik eher in Form eines Kommentars formuliert wird.

Die zweite Hypothese geht der Frage nach, ob sich die „Kriterien“, nach denen YouTube Videos in die Trends aufnimmt, anhand der Metadaten numerisch erfassen lassen. Da der zugrunde liegende Algorithmus nicht öffentlich einsehbar ist, handelt es sich gewissermaßen um einen Blick in eine Blackbox. Neben den klassischen Kennzahlen sollen dabei auch weitere Merkmale wie die Videolänge auf Muster untersucht werden. Hintergrund ist die Monetarisierung auf der Plattform: Die maximale Anzahl an Werbeplätzen steht erst ab einer Laufzeit von zehn Minuten zur Verfügung, während bei kürzeren Videos lediglich Pre- und Post-Roll-Werbung sowie Banner geschaltet werden können. Es liegt daher nahe, dass sich bei erfolgreichen Videos eine Häufung von Laufzeiten knapp über dieser Grenze zeigt. Zudem begünstigt eine hohe Uploadfrequenz, etwa ein täglicher statt eines monatlichen Uploads, dass Videos eines Kanals auf der Startseite und in der Seitenleiste empfohlen werden.

Aus diesem Zusammenhang leitet sich die dritte Hypothese ab: Es wird angenommen, dass die Mehrheit der Trendvideos von Kanälen stammt, die mit mehreren Videos in den Trends vertreten sind, und nicht von Kanälen, die nur ein einziges Trendvideo aufweisen. Sollte sich diese Annahme bestätigen, wäre dies ein Hinweis darauf, dass etablierte Kanäle mit regelmäßigen Uploads strukturell bevorzugt werden und die Trends weniger offen für neue oder kleinere Kanäle sind, als es der Begriff zunächst vermuten lässt.

Die vierte Hypothese bezieht sich auf die Struktur der Kommentare und knüpft an die Arbeit von Schultes (o. J.) an. Dieser ging davon aus, dass ein hoher Anteil negativ Kommentierender eine negative Wirkung auf die Wahrnehmung eines Videos hat. In seiner Untersuchung entfielen 30 % der Kommentare auf die Kategorie T2, die hauptverantwortlich für das negative Gesamtbild war. Gleichzeitig stellte Schultes (o. J.) fest, dass keine Kommentarkategorie insgesamt dominierte, sondern die Verteilung von der jeweiligen Videokategorie und dem Inhalt abhing. Ziel dieser Arbeit ist es, die Untersuchung zu replizieren, wobei ein ähnliches Ergebnis erwartet wird.

Die fünfte Hypothese betrifft das Ranking innerhalb der Trends. Es wird erwartet, dass Videos auf den Plätzen eins bis zehn einen höheren Zuwachs an Aufrufen verzeichnen als Videos auf den Plätzen 40 bis 50, deren Zuwachs vergleichsweise gering ausfallen dürfte. Begründet wird diese Annahme damit, dass die oberen Plätze beim Aufruf der Trendseite ohne weiteres Scrollen sichtbar sind und dadurch mehr Aufmerksamkeit erhalten. Die Platzierung wäre damit nicht nur Folge, sondern zugleich Ursache steigender Aufrufzahlen.

Um diese Hypothesen überprüfen zu können, wird ein technisches Konzept für die Datenerhebung benötigt. Geplant ist eine modular aufgebaute Webanwendung, die unabhängig von einer konkreten Datenbank funktioniert, sodass einzelne Komponenten bei Bedarf ausgetauscht werden können. Als Datenquelle dient die offizielle YouTube-API in der kostenlosen Version, die alle für die Untersuchung benötigten Informationen in strukturierter Form bereitstellt. Diese stellt ein Kontingent von 10.000 Einheiten pro Tag zur Verfügung, das jeweils um Mitternacht pazifischer Zeit zurückgesetzt wird. Eine Abfrage der Trendliste, die die 50 bestplatzierten Videos samt Metadaten in geordneter Reihenfolge liefert, kostet sieben Einheiten, während jede Anfrage nach Kommentar-Threads drei Einheiten verbraucht.

Die Trendliste ändert sich etwa alle 15 Minuten, also rund viermal pro Stunde [3]. Dennoch wird ein stündliches Abrufintervall gewählt. Dabei handelt es sich um einen bewussten Kompromiss, da bei einem häufigeren Abruf der Trendliste nicht mehr genügend Kontingent für eine ausreichende Menge an Kommentaren übrig bliebe. Die API liefert pro Anfrage maximal 100 Kommentar-Threads. Weitere Kommentare lassen sich abrufen, indem das in der Antwort enthaltene „nextPage“-Token als Parameter an die folgende Anfrage übergeben wird.

Als Alternative zur API kommt grundsätzlich auch Scraping in Betracht. Dieses unterliegt keinen Kontingentgrenzen, wobei allerdings der Traffic pro IP-Adresse beachtet werden muss, ist in der Umsetzung jedoch deutlich aufwendiger. Der statische HTML-Code ließe sich mit Beautiful Soup auslesen, die dynamisch nachgeladenen Kommentare wären hingegen nur über einen virtuellen Browser wie Selenium zugänglich. Ein weiterer Nachteil besteht darin, dass beim Scraping einige Funktionen der API fehlen. So lassen sich Ländersperren lediglich lokal feststellen, während die API eine vollständige Liste der erlaubten und gesperrten Länder bereitstellt. Hinzu kommt, dass Änderungen am Seitenaufbau von YouTube den Scraper jederzeit unbrauchbar machen können, während die Schnittstelle der API vergleichsweise stabil und dokumentiert ist. Aus diesen Gründen wird die API als Datenquelle bevorzugt.

Für die Speicherung der Daten wird eine dokumentenbasierte NoSQL-Datenbank eingesetzt. Ausschlaggebend dafür ist zum einen die schnell wachsende Datenmenge, die bei stündlichen Abrufen entsteht. Zum anderen können die JSON-Antworten der API ohne Zwischenschritte und ohne festes Schema direkt in der Datenbank abgelegt werden, was die Implementierung vereinfacht und Flexibilität bei späteren Änderungen der API-Struktur bietet.
